# AGENTS.md

Guidance for AI coding agents (and humans) working on this repository. Humans find the same
rules with step-by-step guides in `CONTRIBUTING.md`; `docs/ARCHITECTURE.md` explains how the
code fits together.

## Project

Edith is a terminal text editor written in C++17:
pull-down menus, dialogs, mouse support, split windows and tabs, line numbers, syntax
highlighting with tree-sitter for more than 50 languages and an optional Vim mode
(Options > Vim Mode, `edith --vim`). `make` builds a normal, dynamically linked binary;
`make STATIC=1` links it statically, which the release builds (`.deb`, AppImage, tarball in
`packaging/`) use so that they run on every Linux distribution. Libraries are allowed; prefer
ones that the common distributions package and that can also be linked statically, and keep
the grammars and queries compiled into the binary (no data files at run time).

**External programs are optional:** Edit > Reformat Code (`src/format.cpp`) calls an installed
standard formatter (clang-format, ruff, gofmt, prettier, ...) if there is one. Everything must
keep working without them (built-in JSON formatter, re-indenting by the syntax tree). The
system clipboard (`src/clipboard.cpp`) uses `pbcopy`/`pbpaste` on macOS and `wl-copy`/`wl-paste`,
`xclip` or `xsel` on Linux when one is installed and Edith does not run over SSH; without them
it asks the terminal (OSC 52) and falls back to Edith's own clipboard. No other feature may
depend on external programs.

## Language rules

- **Source code, comments, identifiers, commit messages, scripts, build files and
  documentation are written in English.** This file is in English as well.
- **The user interface supports US English, German, French, Spanish, Italian, Hungarian,
  Polish and Klingon** (codes `en de fr es it hu pl tlh`, list in `uiLanguages()`). Every
  user-visible string is written in US English in the code and wrapped in `tr()` (UTF-32) or
  `trs()` (UTF-8, for printf-style output). Each other language has its table and its help
  text in `src/i18n_<code>.cpp` (`T` and `HELP`); the English help text is `HELP_EN` in
  `src/menus.cpp`. A new UI language needs a `UiLang` value, its file and one line in
  `uiLanguages()` (`src/i18n.cpp`); messages take the list of codes from `uiLanguageCodes()`.
- The UI language is detected automatically from `LANGUAGE`, `LC_ALL`, `LC_MESSAGES` and
  `LANG` (see `detectUiLanguage()`); `--lang=CODE` overrides it. **English is the fallback**
  for all other locales and for strings without a translation.
- When adding or changing a UI string, update **every** language table in the same change
  (the tests fail for a missing or unused translation). Keep printf placeholders (`%d`, `%s`)
  and the `&` hotkey markers; hotkeys must be unique within each menu and in the menu bar in
  every language. Help lines are at most 70 columns wide (the help dialog on 80 columns).
- Klingon uses Okrand's Latin transcription (no pIqaD: terminals cannot show it); its terms
  are built from attested words and are a playful translation, not an official one.

## Build

```bash
tools/fetch-grammars.sh   # once: downloads tree-sitter + grammars into third_party/
make -j$(nproc)           # binary ./edith
make STATIC=1             # statically linked binary (release builds)
make dist                 # source tarball including third_party/ (see packaging/)
make test                 # unit tests (build/edith-tests) and pty end-to-end tests
./edith --ts-check         # loads every grammar and query, reports dropped patterns
```

- Build with `-Wall -Wextra`; the build must stay free of warnings in `src/`.
- `build/ts_registry.inc` is generated by `tools/gen-registry.sh`; never edit it by hand.
- `third_party/` contains downloaded code at pinned versions. Do not edit it by hand; change
  versions or the language list in `tools/fetch-grammars.sh` instead.

## Conventions

- C++17, 4-space indentation, 120 columns, braces on the same line; match the surrounding
  code. Text is stored as UTF-32 (`u32` = `std::u32string`); convert at the I/O boundaries.
- No ncurses: all terminal output goes through `Screen` (diffed against the previous frame),
  all input through `readKeyRaw()` / `getKey()`.
- Colors use ANSI indexes 0–15 (`Col` namespace in `src/screen.h`); true color terminals get
  the original CGA palette. Extra colors after index 15 (`Col::DIMBLACK`) exist only with true
  color; `Screen::sgr()` replaces them with an ANSI color in other terminals.
- Highlight classes (`H_*` in `src/languages.h`) map to foreground colors via `HLCOL`.
  tree-sitter capture names are mapped to classes in `tsCaptureClass()`.
- Adding a language: add an entry to `LANGS` (`src/languages.cpp`) for detection; if a
  tree-sitter grammar exists in nvim-treesitter, add it to `LANGS` in
  `tools/fetch-grammars.sh` and map it in `TS_FOR_LANG` (`src/treesitter.cpp`). Add its
  standard formatter to the table in `src/format.cpp` (and to `indentSignificant()` if its
  indentation has a meaning).
- The queries (`highlights.scm`, `injections.scm`, `indents.scm`) come from nvim-treesitter at
  the pinned commit; `tools/fetch-grammars.sh --queries` refreshes only them.
  `TsDoc::indents()` is a port of nvim-treesitter's `indent.lua`; keep it in line with it.
- Keep the editor responsive: highlighting only queries the visible range; parsing is
  incremental. Check typing latency on large files after changes to the highlighting path.

## Windows and tabs

- A `Doc` is a buffer (text, undo, highlighting), a `Win` shows a `Doc` with its own cursor and
  scroll position (`View`), a `Tab` has a layout tree of rows and columns (`Node`) with windows
  as leaves. Several windows may show the same `Doc`; a `Doc` exists as long as a window
  shows it (no hidden buffers).
- The buffer of the active window is checked out into `App::ed`: all editing code and the Vim
  engine work on `App::ed`. `App::activate()` swaps the texts when the window changes. Use
  `App::textOf(doc)` to reach the text of any buffer and never keep references to `App::ed`
  across a window switch. Highlighting state lives in `Doc` (`doc()` is the active one).
- `tx() ty() th() tw()` are the geometry of the active window; `layoutAll()` computes all
  rectangles (call it after changing the layout or the screen size).
- Window and tab features work without Vim mode (Window menu, F6, Ctrl+W, Ctrl+T,
  Ctrl+PgUp/PgDn, mouse) and with it (Ctrl-W commands, `gt`, Ex commands through
  `VimHost::layout()`).

## Vim mode

- Vim's documentation (`:help`) is the reference for the semantics of every command, option
  and message. Prefer Vim's behavior over "similar" behavior, including edge cases such as
  `cw` acting like `ce`, exclusive motions that end in column 0, the small delete register,
  failing motions that flush typeahead (and so end a macro) and `.` with a new count.
- The engine (`Vim`) only knows the `Editor` and a `VimHost`; everything the application must
  do (clipboard, dialogs, quitting, language detection) goes through `VimHost`. The tests use
  the default host, so keep the engine free of `App`, `Screen` and terminal code.
- Keys are code points inside the engine (`VK` namespace in `src/vim.h`). Typed keys go through
  `Vim::feed()`; mappings are resolved in `Vim::process()`.
- Buffer changes go through the primitives in `vim.cpp` (`setLine`, `insLines`, `delLines`,
  `replaceLines`, `insText`, `delText`) so that marks, the jump list and `:g` follow the text,
  and every change command is wrapped in `beginChange()` / `endChange()` (one undo step,
  nothing recorded when nothing changed).
- Vim messages are UI strings: wrap them in `tr()` and translate them (keep the `Exxx:` codes).
  Exception: Vim's easter eggs (`:help!`, `:help 42`, `:Ni!`, `:smile`, ...) stay in English.
- In Vim mode Ctrl+S, Ctrl+Q, the function keys, Alt+menu letters and all Cmd keys stay with
  the application.

## macOS

- `g_macKeys` (true on macOS) turns on the Mac's keys in `macKey()` (`src/terminal.cpp`):
  Option+←/→ move by word, Cmd+←/→ and Cmd+↑/↓ become Home/End and Ctrl+Home/End, ESC b / ESC f
  (Terminal.app's Option+←/→) move by word. The Cmd shortcuts (`M_CMD`, only with the kitty
  keyboard protocol) are in `App::shortcut()` on every platform. The help shows the sections
  `HELP_MAC` only when `g_macKeys` is set; tests set it to check them.

## Testing

`make test` builds `build/edith-tests` (every object of `src/` except `main.o`, linked with
`tests/*.cpp`) and runs it, then runs `tests/pty_test.py` against the real binary.
`build/edith-tests name ...` runs only the tests whose name or file contains one of the words.

**Every new feature and every bug fix comes with tests in the same change.** A change is not
done while `make test` fails. When you add a function, a key, a menu entry, a dialog, an Ex
command, an option or a UI string, add or extend the test that covers it.

- `tests/test.h`: `TEST(name)`, `CHECK(c)`, `CHECK_EQ(a, b)`; `sendKeys()` writes raw bytes to
  stdin (a pipe), so application tests go through the real input decoder. Use `"\x1b[27u"` for
  Escape in byte sequences (a lone `"\x1b"` followed by more bytes is read as Alt+key).
- `tests/vimtest.h`: `VT t("text with ‸ cursor"); t.k("dw"); CHECK_EQ(t.state(), "...")`.
  Keys use Vim notation (`<Esc>`, `<CR>`, `<C-v>`). Inside typed Ex commands that must contain
  key names (`:map`, `:exe`), write `<lt>Esc>`, otherwise the key itself is typed.
- `tests/test_app.cpp`: `AppT` drives the whole application (menus, dialogs, mouse, files) and
  inspects the screen buffer.
- `tests/apptest.h`: `AppT` for application tests; `tests/test_windows.cpp` covers windows and
  tabs, `tests/test_windows_fuzz.cpp` mixes random window, tab and editing commands.
- `tests/test_process.cpp`: `runCommand()` and `runShell()`.
- `tests/pty_test.py`: end-to-end checks of the binary in a pseudo terminal in every language
  and of the command line options.
- The tests also check that every `tr()`/`trs()` string is translated in every language with
  the same placeholders, that menu hotkeys are unique, that menus and dialogs show their texts
  completely in every language and that all grammars load without dropped patterns.
- Vim tests describe Vim's behavior. If a test and the engine disagree, check Vim's
  documentation before changing either.
- `tests/test_vim_fuzz.cpp` feeds random key sequences to the Vim engine and checks that the
  cursor and buffer stay valid. After larger changes to the engine run it longer, e.g.
  `EDITH_FUZZ_RUNS=100000 EDITH_FUZZ_SEED=12345 build/edith-tests vim_fuzz`, ideally also with a
  build of the tests using `-fsanitize=address,undefined`.

Before finishing a change, check at least:

- `make test` passes,
- the change in the UI languages (at least `--lang=en` and `--lang=de`; the tests cover all),
- that `./edith --ts-check` still reports no dropped patterns after grammar or query updates,
- a clean, warning-free `make clean && make`,
- an entry in `CHANGELOG.md` under "Unreleased" for user-visible changes (one line per entry,
  no line breaks: the section becomes the GitHub release notes).

## Releasing a new version

Every new version (Semantic Versioning) is released with a version tag; only tags of the form
`v1.2.3` start `.github/workflows/release.yml`, which publishes the release right away.

1. Set the version number everywhere it appears:
   - `src/version.h` (`EDITH_VERSION`: `--version` and Help > About take it from there),
   - `docs/edith.1` (header line, also its date),
   - `packaging/arch/PKGBUILD` (`pkgver`, `pkgrel=1`),
   - `site/index.html` (the download button, the download links of the static binary and the
     AppImage, the status line at the bottom),
   - `README.md` and the help texts if they name a version or versioned file names.

   Then search for the old number to find places not listed here (and add them to this list):
   `git grep -nF 1.2.2 -- ':!third_party' ':!CHANGELOG.md'`. The test `version_is_consistent`
   compares the known places with `src/version.h`.
2. `CHANGELOG.md`: move the entries under "Unreleased" to a new section `## [1.2.3] - DATE`
   (it becomes the release notes) and leave an empty "Unreleased" section above it.
3. `make test` must pass. Commit, then tag and push both:
   `git tag v1.2.3 && git push origin master v1.2.3`.
